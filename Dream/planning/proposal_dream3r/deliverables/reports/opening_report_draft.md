# 开题报告草稿

## 题目

面向前馈式三维重建模型的聚合管理平台设计与实现

## 一、课题背景与问题提出

DUSt3R 之后，三维重建逐步从传统的多阶段几何流程，转向端到端的前馈式模型推理。此类模型可以直接从图像对、多视图图像或视频序列中输出点图、深度、相机位姿或场景相关结果，降低了三维重建实验的入门门槛。

但在实际使用中，模型能力仍然分散在论文 demo、独立仓库和命令行脚本中。不同模型的环境、权重、输入格式、输出目录和运行命令差异较大。研究人员如果要比较 DUSt3R、MASt3R、MonST3R、Spann3R、Fast3R、CUT3R 等模型，通常需要反复配置环境、手动运行命令、复制日志和整理产物。这个过程成本高，且结果难以复现。

本课题关注的不是提出新的三维重建算法，而是解决多模型实验流程的工程化问题。平台目标是把前馈式三维重建模型从分散脚本中抽取出来，形成可运行、可复现、可对比、可扩展的统一工作流程。

## 二、研究目标

本课题拟设计并实现一个面向前馈式三维重建模型的聚合管理平台。平台围绕“模型接入、任务提交、远端执行、日志监听、结果回传、对比查看”形成闭环。

主要目标如下：

1. 统一模型接入方式。用统一描述记录模型环境、权重路径、运行命令、输入要求和输出目录，使新模型接入不再依赖临时修改平台代码。
2. 统一任务调度流程。支持本地提交任务，通过 SSH/SCP 将输入和配置发送到远端 GPU 服务器，并跟踪远端运行状态。
3. 统一结果归集方式。将点图、mask、日志、元数据和输出文件集中管理，保留任务复现依据。
4. 支持多模型横向对比。在同一输入条件下查看不同模型的耗时、状态、产物和元数据。
5. 预留 API 与导出能力。将稳定的实验能力封装为后续应用可调用的接口，并支持报告或结果包导出。

## 三、研究内容

### 1. 模型管理与注册

平台需要维护模型池，记录每个模型的基本信息、状态、输入输出类型、远端路径、环境名称、权重情况和接入进度。开题阶段规划优先覆盖代表性 3R 模型：

- DUSt3R / MASt3R：图像对和静态多视图重建；
- Fast3R / Spann3R：多图输入、长序列或空间记忆重建；
- MonST3R / CUT3R：动态场景、视频或在线持续重建；
- Align3R 等候选模型：根据权重和环境情况后续补充。

模型接入重点不是简单堆叠模型数量，而是在统一条件下组织输入、输出和对比记录。

### 2. 任务工作流设计

平台任务由本地侧和远端侧共同完成：

- 本地侧负责导入样本、选择模型、设置参数、生成任务配置、查看状态和归集结果；
- 远端侧负责接收输入、执行模型推理脚本、输出结果文件、写入日志和元数据。

一次任务应覆盖输入准备、任务提交、远端执行、日志监听、结果回传和产物解析。平台保留任务配置和状态文件，减少手动命令带来的不可复现问题。

### 3. 统一执行合同

为降低模型差异带来的接入成本，开题阶段设计统一执行合同。核心文件包括：

| 文件 | 作用 | 平台使用方式 |
| --- | --- | --- |
| `job.json` | 记录模型、输入、参数和输出目录 | 作为任务提交与复现依据 |
| `status.json` | 记录运行状态、进度和错误信息 | 用于状态刷新与失败诊断 |
| `scene_meta.json` | 记录结果产物、相机与场景信息 | 用于结果展示与横向对比 |

通过该合同，新模型只需要实现执行器接口并产出约定文件，平台层保持统一的提交、跟踪、归集和导出逻辑。

### 4. 结果管理与对比

平台围绕样本、模型、任务和结果四类对象组织功能。样本用于统一输入条件，模型用于记录接入状态，任务用于记录运行过程，结果用于查看产物和对比数据。

中后期需要实现样本矩阵和模型对比视图，使同一输入下的多模型结果可以横向查看。对比内容不包装为算法性能结论，而是记录运行耗时、输出完整性、日志状态、产物类型和可视化结果。

## 四、技术路线与系统方案

平台采用桌面前端、本地后端、远端调度和模型执行器分层设计。

| 层级 | 技术与职责 |
| --- | --- |
| 桌面前端 | Tauri 2 + React，负责任务配置、队列查看、结果查看和系统设置 |
| 本地后端 | FastAPI，负责模型注册、任务队列、合同校验、API 和 WebSocket |
| 远端调度 | SSH / SCP，负责上传输入、启动任务、监听日志和同步产物 |
| 模型执行器 | Python runner，封装不同模型的命令、参数、输出目录和元数据 |

该方案的边界是：平台支撑模型实验、部署和结果管理，不替代模型本身的算法贡献。

## 五、验证方案

平台验证以可运行、可复现、可对比为标准，不把平台结果写成模型性能结论。

验证内容包括：

1. 功能闭环：模型注册、任务提交、日志刷新、结果回传均可运行。
2. 稳定性：远端任务失败、取消和异常退出时有明确状态记录。
3. 可复现性：任务配置、输入、参数、日志和结果目录可追踪。
4. 对比可用性：同一输入下可以保留多模型结果，并支持横向查看。
5. 扩展性：新增模型时主要修改执行器和模型描述，而不是重写平台主体。

## 六、阶段计划

| 阶段 | 工作重点 | 主要产物 |
| --- | --- | --- |
| 开题阶段 | 明确平台定位、研究目标、功能边界和技术路线 | 开题报告、系统方案、模型接入计划 |
| 原型阶段 | 搭建前端工作台、本地后端、任务合同和基础执行器 | 可运行平台原型、基础任务流程 |
| 中期阶段 | 补充模型接入、完善任务记录、验证远端运行和结果回传 | 中期报告、运行截图、测试记录 |
| 后期阶段 | 完善对比视图、导出能力、系统文档和论文材料 | 最终系统、说明文档、论文或结题材料 |

## 七、风险与应对

| 风险 | 表现 | 应对方式 |
| --- | --- | --- |
| 模型环境差异大 | 不同模型依赖、CUDA、权重路径不一致 | 用模型蓝图和执行器隔离差异 |
| 远端任务不可控 | SSH 中断、任务失败、日志缺失 | 保留状态文件、日志文件和错误信息 |
| 输出格式不统一 | 不同模型输出点云、深度、mask 或视频 | 通过 `scene_meta.json` 描述产物索引 |
| UI 与真实流程脱节 | 界面展示与实际任务状态不一致 | 以端到端任务状态驱动界面 |
| 证据链不完整 | 报告缺少截图、日志和测试依据 | 保留配置、日志、测试输出和打包记录 |

## 八、预期成果

预期完成一个可运行的平台原型，支持代表性前馈式三维重建模型的统一接入、任务提交、远端执行、日志监听和结果管理。最终产物包括：

1. 平台原型与主要功能界面；
2. 代表模型接入样例；
3. 任务合同与执行器接口；
4. 实验运行记录和验证材料；
5. 系统说明文档、接口文档和报告材料。

## 九、开题阶段结论

本课题的核心工作是把前馈式三维重建模型的实验流程工程化。开题阶段已明确平台边界：不做新的模型算法，而是围绕多模型实验的部署、调度、记录和对比建立统一入口。后续工作应以真实任务闭环、可复现记录和模型接入验证作为主要依据。
